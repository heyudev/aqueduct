# Aqueduct 详细设计

> 面向要照着实施、测试、值班的人。整体架构和选型理由见 [hld.md](hld.md)。
>
> 标注「待实测」的地方是设计时无法确定、必须在真机上验证后回填的。**回填前不要把这些数字当事实用。**

## 1. 对外接口契约

这一节是业务方接入的依据，也是平台侧不能随意破坏的承诺。

### 1.1 端点

服务地址 `http://<gateway>:4000`，协议与 OpenAI API 一致。

| 端点 | 方法 | 状态 | 说明 |
|---|---|---|---|
| `/v1/chat/completions` | POST | 阶段 1 提供 | 主力接口，支持流式与工具调用 |
| `/v1/models` | GET | 阶段 1 提供 | 列出当前 key 可访问的逻辑模型 |
| `/v1/embeddings` | POST | 阶段 3 提供 | 向量化 |
| `/v1/completions` | POST | 不提供 | 老式补全接口，新接入一律用 chat |
| `/health/liveliness` | GET | 阶段 1 提供 | 网关存活探针，无需鉴权 |

**接入示例**

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://aqueduct.internal:4000/v1",
    api_key="sk-aq-...",
)
resp = client.chat.completions.create(
    model="aqueduct-chat",
    messages=[{"role": "user", "content": "你好"}],
)
```

### 1.2 逻辑模型名

业务方只能使用逻辑名，真实模型名不对外暴露。

**命名规范**：`aqueduct-<能力>[-<版本>]`

| 逻辑名 | 能力定位 | 上线阶段 |
|---|---|---|
| `aqueduct-chat` | 默认通用模型，能力优先 | 阶段 1 |
| `aqueduct-fast` | 简单任务，成本和延迟优先 | 阶段 3 |
| `aqueduct-embed` | 文本向量化 | 阶段 3 |

**版本与灰度**：需要换底层模型时，先加带版本后缀的新逻辑名（如 `aqueduct-chat-v2`），让愿意尝鲜的业务方主动切换验证。验证通过后，把不带后缀的 `aqueduct-chat` 指向新模型，旧模型保留带版本的名字（`aqueduct-chat-v1`）一段时间。

**弃用流程**：提前两周通知使用该名字的 key 持有者 → 通知期内在响应头加 `X-Aqueduct-Deprecated` 标记 → 到期下线。查谁在用：见 §5.2 的用量查询。

不带版本后缀的名字是**滚动指针**，业务方要接受它背后的模型会变。需要稳定行为的场景（如已经调好提示词的线上功能）应当固定使用带版本的名字。

### 1.3 参数支持

网关开启了 `drop_params`，未知参数被丢弃而不是报错——这样各家 SDK 发的 OpenAI 专有字段不会导致调用失败。**但被丢弃的参数是静默失效的**，业务方不会收到警告。

| 参数 | 支持 | 说明 |
|---|---|---|
| `messages` | 是 | 支持 system / user / assistant / tool 角色 |
| `stream` | 是 | SSE，见 §1.5 |
| `temperature` `top_p` `max_tokens` | 是 | |
| `stop` | 是 | |
| `tools` `tool_choice` | 是 | 取决于底层模型是否支持工具调用，选型时需确认 |
| `response_format` | 部分 | JSON 模式由 vLLM 的结构化输出支持，需实测确认行为 |
| `seed` | 部分 | 不保证跨版本可复现 |
| `n` | 否 | 一次生成多个候选，会成倍消耗算力，禁用 |
| `logprobs` | 待定 | 阶段 1 不承诺 |
| `frequency_penalty` `presence_penalty` | 是 | |

`max_tokens` 未指定时，vLLM 会一直生成到模型自然停止或触及 `MAX_MODEL_LEN`。**要求业务方显式设置**，否则一次跑飞的调用会长时间占用 KV cache 影响所有人。

### 1.4 错误码

约定如下语义。**LiteLLM 的实际返回码需在首次部署时逐个验证并回填**，尤其是预算超限——不同版本可能返回 400 或 429。

| 码 | 含义 | 业务方应该怎么做 |
|---|---|---|
| 400 | 请求格式错误、参数非法、超出上下文长度 | 修代码，重试无用 |
| 401 | key 无效或已吊销 | 联系平台侧 |
| 403 | key 有效但无权访问该逻辑模型 | 申请授权 |
| 429 | 触发限流或预算用尽 | 指数退避重试；持续 429 说明配额不够，申请扩额 |
| 500 | 网关或推理层内部错误 | 退避重试，重试三次仍失败则告警 |
| 503 | 无健康后端（模型正在重启或全部故障） | 退避重试，这通常是平台侧的维护窗口 |
| 504 | 超时 | 退避重试；长上下文请求容易触发，考虑缩短输入 |

**给业务方的硬性要求**：必须处理 5xx 和超时，关键路径必须有降级方案。这是单点架构下的前提条件，不是建议。

### 1.5 流式

`stream: true` 时返回 SSE，格式与 OpenAI 一致：每行 `data: {json}`，以 `data: [DONE]` 结束。

需要注意的两点：

- **首个 chunk 的等待时间就是 TTFT。** 在 H20 上，长输入时这个等待可能有数秒，客户端不要设置过短的读超时。
- **流式过程中出错时，HTTP 状态码已经是 200 了。** 错误只能以 SSE 事件的形式出现在流中间。客户端必须处理"流到一半断掉"的情况，不能只看状态码。

### 1.6 超时、重试与限流

| 环节 | 设置 | 位置 |
|---|---|---|
| 网关到后端超时 | 900s | `request_timeout`，`gateway/config.yaml` |
| 网关自动重试 | 2 次 | `num_retries`，仅对可重试错误 |
| 后端摘除阈值 | 连续 3 次失败 | `allowed_fails` |
| 摘除后冷却 | 30s | `cooldown_time` |
| 每 key 限流 | 签发时设置 | 见 §4.2 |
| 后端 RPM 上限 | 600 | 每个后端条目的 `rpm`，防止单实例被打满 |

900 秒的超时看起来很长，但 H20 上长上下文加长输出的组合确实可能跑几分钟。宁可让慢请求跑完，也不要在业务方那边留下莫名其妙的截断。

## 2. 配置项

三处配置，职责不重叠。改任何一处前先确认改的是不是地方。

| 文件 | 管什么 | 改动后如何生效 |
|---|---|---|
| `.env` | 密钥、地址、路径等环境相关值 | 重启对应服务 |
| `inference/vllm/models/<name>.env` | 单个模型的加载和调度参数 | `make down-model && make up-model` |
| `gateway/config.yaml` | 逻辑模型到后端的映射、路由与限流策略 | `make restart-gateway` |

### 2.1 环境变量（.env）

完整清单见 [`.env.example`](../../.env.example)，此处只说明容易配错的几项。

| 变量 | 易错点 |
|---|---|
| `VLLM_PRIMARY_URL` | 必须是**网关容器**能访问到的地址。同机部署时写宿主机内网 IP，写 `127.0.0.1` 会指向容器自己 |
| `GATEWAY_BIND` | 默认 `127.0.0.1` 只监听本机。改成 `0.0.0.0` 前先确认有防火墙限制来源 |
| `VLLM_BIND` | **不要**改成 `0.0.0.0` 除非有防火墙。vLLM 无配额，直连即可打满机器 |
| `MODEL_DIR` | 必须在本地 NVMe 上。网络存储会让权重加载时间从几分钟变成一小时 |
| `SHM_SIZE` | 低于几十 GB 会导致 TP 启动时**无报错挂起** |
| `VLLM_IMAGE_TAG` | 上线前锁到实测过的版本，不要留 `latest` |

### 2.2 模型参数

以 [`inference/vllm/models/primary.env`](../../inference/vllm/models/primary.env) 为例。每一项都给了取值依据，调整时按依据判断，不要凭感觉试。

| 参数 | 起始值 | 依据 | 调整方向 |
|---|---|---|---|
| `TP_SIZE` | 8 | 单机 GPU 数，NVLink 全互联 | 不要超过实际卡数 |
| `GPU_MEM_UTIL` | 0.92 | 留 8% 给 CUDA context 和 NCCL 缓冲 | 上调需谨慎，OOM 会在压测中途才出现 |
| `MAX_MODEL_LEN` | 65536 | 通用场景够用，且不过度挤占 KV cache | 有真实长文需求再加，加完重新测并发 |
| `KV_CACHE_DTYPE` | fp8 | KV 显存减半，换来约两倍并发 | 质量回归发现劣化就改回 `auto` |
| `MAX_NUM_BATCHED_TOKENS` | 4096 | **H20 关键参数**，见下 | 见下 |
| `MAX_NUM_SEQS` | 64 | 调度器准入上限，防止超发 | 实测 KV cache 有余量再加 |
| `EXTRA_ARGS` | `--enable-expert-parallel` | MoE 专家分散到多卡而非复制 | 稠密模型时去掉 |

**`MAX_NUM_BATCHED_TOKENS` 为什么是 4096**

这个参数控制每个调度步骤处理多少 token。H100 配置里常见 8192–16384，直接照抄到 H20 上是错的：H20 算力只有 H100 的约 1/7，同样大小的块要算 7 倍长的时间，而在这个块算完之前，所有正在解码的请求都在等。

结果就是长输入请求一来，所有人的输出都卡顿一下。4096 是在「预填充吞吐」和「解码延迟平滑度」之间的起始折中。

**怎么调**：压测时同时看 TTFT 和 TPOT。TTFT 太高而 TPOT 有余量 → 调大；TPOT 出现周期性尖刺 → 调小。

### 2.3 网关配置

`gateway/config.yaml` 的结构：

```yaml
model_list:          # 逻辑模型 → 后端映射，同名多条即自动负载均衡
general_settings:    # 主密钥、数据库、健康检查
litellm_settings:    # 全局行为：超时、重试、日志、回调
router_settings:     # 路由策略、故障摘除
```

加一个后端副本 = 在 `model_list` 里加一条 `model_name` 相同、`api_base` 不同的条目。加一个新模型 = 加一条 `model_name` 不同的条目。就这两种操作。

## 3. 容量计算

不要拍脑袋估并发。用下面的方法算出一个起点，再用压测校准。

### 3.1 显存预算

```
单卡显存 × 卡数 = 总显存
总显存 × GPU_MEM_UTIL = vLLM 可用
vLLM 可用 - 模型权重 = KV cache 可用
```

以 8×96GB、`GPU_MEM_UTIL=0.92`、235B 模型 FP8 为例：

```
768 GB × 0.92 = 706 GB  可用
706 GB - 235 GB (权重) = 471 GB  给 KV cache
```

FP8 权重大小约等于「参数量 × 1 字节」。实际下载后用 `du -sh` 核对，MoE 模型的权重文件往往比参数量估算略大。

### 3.2 KV cache 与并发

每个序列每 token 占用：

```
bytes/token = 2 × num_kv_heads × head_dim × num_layers × dtype_bytes
```

`2` 是 K 和 V 两份。前四个参数从模型仓库的 `config.json` 里读：`num_key_value_heads`、`hidden_size / num_attention_heads`（即 head_dim，部分模型直接给 `head_dim`）、`num_hidden_layers`。`dtype_bytes` 在 `KV_CACHE_DTYPE=fp8` 时是 1，`auto`（bf16）时是 2。

算例，假设 94 层、4 个 KV head、head_dim 128、FP8：

```
每 token  = 2 × 4 × 128 × 94 × 1 = 96,256 B ≈ 94 KB
32k 上下文 = 94 KB × 32768 ≈ 3.1 GB / 序列
理论并发   = 471 GB ÷ 3.1 GB ≈ 152 路
```

**这个数字是上界，实测会低不少**，因为还有激活内存、调度碎片、以及并非所有请求都用满上下文。按理论值的 50%–70% 作为规划值，然后用压测校准。

采用 MLA 等新型注意力结构的模型（如 DeepSeek 系列）KV cache 占用远低于上式，需按其具体结构单独计算。

### 3.3 前缀缓存的影响

前缀缓存不省 KV cache 空间（缓存本身就住在 KV cache 里），省的是预填充算力。

它对容量规划的影响是间接但巨大的：命中率高时，同样的 GPU 能扛住多得多的请求，因为大部分请求根本不需要预填充。这也是为什么要推动业务方稳定系统提示词——**这是不花钱的扩容**。

压测时务必分别测「全新前缀」和「共享前缀」两种场景，两个数字都记录。

## 4. 关键流程

### 4.1 推理请求

```
调用方          网关                    vLLM               PostgreSQL
  │              │                       │                    │
  ├─ POST ──────>│                       │                    │
  │              ├─ 验 key                │                    │
  │              ├─ 查权限与预算 ─────────────────────────────>│
  │              │<────────────────────────────────────────────┤
  │              │  (不通过则直接返回 401/403/429)             │
  │              ├─ 选后端（最少在途）    │                    │
  │              ├─ 转发 ────────────────>│                    │
  │              │                       ├─ 查前缀缓存         │
  │              │                       ├─ 分块预填充         │
  │              │                       ├─ 解码（与其他请求交错）
  │              │<── SSE 流 ────────────┤                    │
  │<─ SSE 流 ────┤                       │                    │
  │              ├─ 写用量流水 ──────────────────────────────>│
```

预算检查在请求**之前**，用量记账在请求**之后**。这意味着预算是软限制：一个正在进行的大请求可以超出预算完成，下一次调用才会被拒。对内部服务这个精度够了。

### 4.2 API key 生命周期

**签发**

```bash
TEAM=search BUDGET=200 MODELS=aqueduct-chat ./scripts/mint-key.sh
```

签发时确定四项：`key_alias`（`aqueduct-<team>`，用于查账）、可访问模型列表、周期预算、周期长度（默认 30 天滚动）。

key 明文只在签发时显示一次，数据库存哈希。丢失只能重新签发，无法找回。交付走安全渠道，不要贴在群里。

**用量与告警**

```bash
make usage    # 各 key 的累计消耗
```

预算的作用是兜底：内部服务没有真实按次成本，预算的真正价值是**拦住写错的死循环**。所以额度不必精算，按「正常用量的 3–5 倍」设置即可，触发了就说明出问题了。

**吊销**：通过 LiteLLM 的 `/key/delete` 接口。人员离职、key 泄露、业务下线三种情况必须吊销。

### 4.3 模型上线与切换

灰度路径，不停服：

1. 新模型权重下好，起一个新的 vLLM 实例，用不同端口。
2. 网关加一条新逻辑名 `aqueduct-chat-v2` 指向它，`make restart-gateway`。
3. 跑冒烟测试和质量回归（§8.3）。
4. 通知 1–2 个业务方切到 `-v2` 试用，观察一周。
5. 把 `aqueduct-chat` 的后端改指新实例，旧实例保留为 `aqueduct-chat-v1`。
6. 观察一到两周无回退需求后，下线旧实例。

单机场景下步骤 1 受显存限制通常做不到（两个大模型放不下），此时只能停服切换：`make down-model` → 改 `MODEL_PATH` → `make up-model`。**停服切换必须提前通知业务方**，并且要保留回滚路径——旧模型权重先别删。

### 4.4 后端故障转移

网关每 60 秒健康检查一次后端。连续 3 次调用失败的后端被摘除，冷却 30 秒后重新尝试。

单后端时摘除等于服务不可用，返回 503。这是已知的单点问题，见 [hld.md](hld.md) 的可用性一节。

## 5. 数据与日志

### 5.1 存储

PostgreSQL 由 LiteLLM 管理表结构，我们不直接建表。关心的是三类数据：

| 数据 | 用途 | 敏感度 |
|---|---|---|
| 虚拟 key（哈希）、别名、权限、预算 | 鉴权与配额 | 高，泄露即越权 |
| 调用流水：时间、key、模型、token 数、耗时、状态 | 查账与容量分析 | 中，含使用模式 |
| 请求/响应正文 | 排障 | **极高，默认不记录** |

**唯一需要备份的组件就是这个数据库。** vLLM 和网关都无状态，重建即可；数据库丢了意味着所有 key 失效、历史用量归零。

### 5.2 用量查询

除了 `make usage`，直接查库可以做更细的分析。常用维度：按 `key_alias` 聚合看各团队消耗、按模型聚合看哪个模型真正被用、按小时聚合看负载曲线以决定扩容时机。

具体表名和字段随 LiteLLM 版本变化，首次部署时用 `\dt` 确认后回填到本节。

### 5.3 日志规范

| 来源 | 记什么 | 不记什么 | 保留 |
|---|---|---|---|
| 网关 | 时间、key 别名、逻辑模型、token 数、耗时、状态码 | **请求与响应正文** | 90 天 |
| vLLM | 启动参数、调度统计、错误堆栈 | 请求正文（`--disable-log-requests` 已开） | 30 天 |
| 数据库 | 慢查询 | — | 30 天 |

排障需要看正文时：临时关闭 `turn_off_message_logging` → 复现问题 → **立即改回并重启**。开启期间要在值班记录里写明起止时间和原因。

## 6. 可观测性

### 6.1 指标

指标名以实际 `/metrics` 输出为准——vLLM 各版本间有变动，尤其是 V0 到 V1 引擎。首次部署时 `curl http://<vllm>:8000/metrics | grep vllm` 确认后回填。

**引擎层（vLLM）——回答"慢在哪一步"**

| 指标 | 看什么 |
|---|---|
| `vllm:time_to_first_token_seconds` | 预填充耗时。H20 的主要短板，重点监控 |
| `vllm:time_per_output_token_seconds` | 解码速度。应该稳定；出现尖刺说明调度被长预填充打断 |
| `vllm:num_requests_running` | 在途请求数 |
| `vllm:num_requests_waiting` | **排队长度。持续大于 0 说明容量不够** |
| `vllm:gpu_cache_usage_perc` | KV cache 使用率。逼近 100% 就是并发上限 |
| 前缀缓存命中率 | **H20 上最值得盯的指标**，低命中率意味着算力全浪费在重复预填充上 |

**业务层（网关）——回答"谁在用、用得对吗"**：按 key 的请求数与 token 数、错误率、网关自身延迟。

**硬件层（DCGM）——回答"是不是机器的问题"**：GPU 利用率、显存占用、温度、功耗、ECC 错误。

### 6.2 告警

阈值待实测后回填，此处先定义**告警条件的形态和响应动作**。

| 告警 | 条件 | 含义与动作 |
|---|---|---|
| 服务不可用 | 网关健康检查失败持续 2 分钟 | 立即处理，查网关与后端状态 |
| 无健康后端 | 503 比例 > 10% 持续 5 分钟 | 推理层挂了或正在重启，查 `make logs-model` |
| 排队积压 | `num_requests_waiting` 持续 > N | 容量不够，需要扩容或限流 |
| KV cache 打满 | `gpu_cache_usage_perc` > 95% 持续 5 分钟 | 同上，先临时调小 `MAX_MODEL_LEN` 缓解 |
| 首 token 劣化 | TTFT P99 超过基线 2 倍 | 查前缀缓存命中率是否掉了 |
| 缓存命中率骤降 | 命中率相对日常基线下降过半 | 多半是某个业务方改了提示词模板 |
| 单 key 用量异常 | 某 key 小时用量超其日常均值 10 倍 | 大概率是死循环，联系业务方 |
| GPU 硬件异常 | ECC 错误增长，或温度持续超阈值 | 报修，不要带病运行 |

**基线从哪来**：阶段 1 压测和第一周运行数据。没有基线的告警只会制造噪音，所以阶段 2 之前不要配"相对基线"这类告警。

## 7. 故障处理

值班时按现象查。详细排查步骤见 [../runbook.md](../runbook.md)。

| 现象 | 最可能的原因 | 首先做什么 |
|---|---|---|
| 全部请求 503 | vLLM 挂了或在重启 | `make logs-model` 看是否 OOM |
| 启动后一直不就绪，无报错 | 共享内存不足，TP worker 挂起 | 查 `SHM_SIZE` 和宿主机 `/dev/shm` |
| 首 token 特别慢 | 前缀缓存没命中，或 `MAX_NUM_BATCHED_TOKENS` 过大 | 看命中率指标 |
| 并发一上来就排队 | KV cache 不够 | 看 `gpu_cache_usage_perc`，按 §3.2 重算容量 |
| 报 model not found | 逻辑名与 `--served-model-name` 不一致 | 比对两处配置 |
| 401 但 key 是对的 | key 已过期或被吊销 | 查数据库中该 key 状态 |
| 429 但预算没用完 | 触发的是 RPM 限流不是预算 | 查后端 `rpm` 设置 |
| 运行一段时间后 OOM | vLLM 显存是启动时预分配的，运行中增长通常是 bug | **先保存 `nvidia-smi` 输出再重启**，考虑上报上游 |
| 输出质量突然变差 | 是否刚换过模型或改过量化设置 | 查变更记录，跑质量回归 |

最后一条值得强调：**不要用重启掩盖问题**。显存泄漏、ECC 错误、莫名的性能劣化，重启都能让现象消失，但根因还在，下次会在更糟的时候复发。

## 8. 测试

### 8.1 冒烟

`make smoke`，五项：网关存活、模型已注册、非流式补全、流式补全、8 路并发。

每次部署、每次改配置、每次换模型后都要跑。全过才算变更完成。

### 8.2 压测

`make bench`，扫不同并发档位，记录 TTFT、TPOT、吞吐。

**必须测两组**，因为它们在 H20 上差异巨大：

1. **全新前缀**：每个请求的提示词都不同，衡量最坏情况的预填充能力。
2. **共享前缀**：所有请求共用一段长系统提示词，衡量前缀缓存生效后的能力。

两组数字之间的差距，就是推动业务方稳定提示词能拿到的收益。把它写进接入文档说服他们。

还要单独测长输入的表现——H20 上 TTFT 随输入长度的增长曲线是这套硬件最需要提前知道的特性。建议至少测 2k / 8k / 32k 三档。

结果填进 [../runbook.md](../runbook.md) 的实测基线表。

### 8.3 模型质量回归

换模型、改量化设置（尤其 `KV_CACHE_DTYPE`）之后必须做，否则容量优化可能是拿质量换的。

方法务实即可：**攒一组 30–50 条内部真实场景的样例**，覆盖主要用途（问答、改写、工具调用、长文档理解），新旧模型各跑一遍，人工比对。不需要学术 benchmark——公开榜单分数高不代表在你的场景上好用。

这组样例攒起来后要长期维护，它是判断"换模型到底是不是进步"的唯一依据。

### 8.4 变更验证清单

任何生产变更后按顺序确认：

- [ ] `make smoke` 全过
- [ ] Grafana 上 TTFT / TPOT / 错误率与变更前对比无劣化
- [ ] 改了模型或量化设置的，跑过 §8.3 质量回归
- [ ] 变更内容、时间、执行人记录在案
- [ ] 回滚路径明确（旧模型权重未删、旧配置可恢复）
