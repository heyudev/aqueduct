# Aqueduct 概要设计

> 状态：设计中，尚未部署。GPU 机器采购中，文档里的所有性能数字都是估算，未经实测。
> 详细实现见 [lld.md](lld.md)，硬件选型依据见 [../hardware.md](../hardware.md)。

## 1. 这是什么

把一批 H20 GPU 服务器变成一个内部人人可调的 OpenAI 兼容 API 服务。业务系统改一个 `base_url` 就能用上开源大模型，平台侧统一管理容量、密钥和用量。

### 要解决的问题

各业务线都想用大模型，各自为战会同时出现三个问题：

- **资源浪费**：每个团队申请自己的机器、自己部署，显卡大部分时间闲置，但谁都不够用。
- **合规风险**：调外部 API 意味着数据出境，密钥散落在各个仓库和配置文件里，没人说得清哪些数据流去了哪里。
- **成本不透明**：算力花在哪个业务上、值不值，拿不出数字。

Aqueduct 把推理能力集中成一个服务，业务方按需调用。这三个问题分别由集中调度、本地部署、按 key 计量来解决。

### 做什么

- 提供 OpenAI 兼容的推理 API：对话补全、文本补全、向量化。
- 按接入方签发独立 API key，绑定可用模型和用量配额。
- 记录每次调用的用量，支持按团队查账。
- 屏蔽底层模型细节：业务方调逻辑名，平台侧可以随时换底层模型。

### 不做什么

明确划在范围外，避免期望错位：

- **不做训练和微调。** 只做推理。
- **不做提示词管理、Agent 编排、RAG 流水线。** 这些是业务侧的事，Aqueduct 只提供模型调用和向量化这两块底层能力。
- **不做多租户强隔离。** 内部服务，所有调用方共享同一批 GPU，一个业务打满负载会影响其他业务。配额限制的是总量，不保证 QoS。
- **不承诺高可用。** 起步是单机单副本，机器维护即服务中断。业务方必须自己处理调用失败。

### 术语

| 词 | 含义 |
|---|---|
| 预填充 / prefill | 处理输入提示词的阶段，一次性算完整段上下文，算力密集 |
| 解码 / decode | 逐个生成输出 token 的阶段，瓶颈是显存带宽 |
| TTFT | 首 token 延迟，从发出请求到收到第一个字的时间，由预填充决定 |
| TPOT | 每输出 token 耗时，决定"打字速度"，由解码决定 |
| KV cache | 推理过程中缓存的中间状态，占显存，是并发数的硬约束 |
| 前缀缓存 / prefix cache | 相同开头的请求复用上一次的预填充结果，跳过重复计算 |
| TP / 张量并行 | 把一个模型切开摊到多张卡上协同计算 |
| MoE | 混合专家模型，参数总量大但每次只激活一小部分 |
| 逻辑模型名 | 业务方调用时写的名字（如 `aqueduct-chat`），与底层真实模型解耦 |

## 2. 整体架构

```
        业务系统 / 内部工具 / IDE 插件
                    │
                    │  OpenAI 兼容协议
                    │  Authorization: Bearer sk-aq-xxx
                    ▼
     ┌───────────────────────────────────┐
     │  网关层  LiteLLM Proxy             │
     │                                   │──── PostgreSQL
     │  验 key → 查配额 → 选后端           │     key / 配额 / 用量流水
     │  → 转发 → 记账                     │
     └───────────────────────────────────┘
                    │  OpenAI 兼容协议，内网
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │ vLLM   │  │ vLLM   │  │ vLLM   │     推理层
   │ 主力   │  │ 副本   │  │ 小模型 │     一实例一模型
   │ 8×H20  │  │ 8×H20  │  │ 1×H20  │
   └────────┘  └────────┘  └────────┘
       └────────────┴────────────┘
                    │  /metrics
                    ▼
          Prometheus + Grafana
```

只有网关层和推理层两层，刻意保持简单。分层的边界是标准的 OpenAI 协议，两边都可以独立替换。

| 层 | 组件 | 职责 | 有无状态 |
|---|---|---|---|
| 网关 | LiteLLM Proxy | 协议兼容、鉴权、配额、路由、记账 | 无状态，状态在 PostgreSQL |
| 推理 | vLLM | 加载模型、批处理调度、生成 | 无状态 |
| 存储 | PostgreSQL | key、预算、调用流水 | 有状态，唯一需要备份的组件 |
| 观测 | Prometheus + Grafana | 指标采集与展示 | 指标数据可丢 |

网关和推理分离带来两个具体好处：加 GPU 机器时只需在网关配置里加一行后端地址，不动其他任何东西；重启或更换模型不影响已签发的 key 和历史用量。

### 一个请求怎么被处理

1. 业务方带 `sk-aq-` 开头的 key 请求 `/v1/chat/completions`，`model` 字段填逻辑名如 `aqueduct-chat`。
2. 网关校验三件事：key 是否有效、是否有权访问这个逻辑模型、周期预算是否用尽。任一不过直接返回错误，不打扰后端。
3. 网关在该逻辑模型对应的若干个 vLLM 实例中选一个转发。只有一个后端时这步是空操作，两个以上时按最少在途请求数选。
4. vLLM 收到请求，检查前缀缓存。命中的部分跳过预填充，未命中的部分走分块预填充，与正在解码的请求交错调度。
5. 生成结果流式返回，原路经网关回到业务方。
6. 请求结束后网关把 token 数、耗时、模型、key 写入 PostgreSQL。**不记录请求和响应正文。**
7. Prometheus 分别从网关和 vLLM 抓指标。

## 3. 关键选型

每项都按「结论 — 理由 — 代价 — 何时重新评估」写，方便以后回头判断决策是否还成立。

### 推理引擎选 vLLM

社区最大、新模型支持最快、文档最全，出问题搜得到答案。开箱即有前缀缓存、分块预填充、连续批处理，这三项正好是 H20 上最需要的能力。

**代价**：极限性能不如 TensorRT-LLM。

**备选与触发条件**：SGLang 在高前缀命中率场景（RadixAttention）和结构化输出上更强，如果实测发现前缀缓存是主要瓶颈，值得单独评估。TensorRT-LLM 需要为每个模型做编译，运维复杂度和上新模型的速度都不匹配起步阶段，暂不考虑。

换引擎的成本很低——推理层通过标准 OpenAI 协议接入，业务方无感知。

### 网关选 LiteLLM 而不是自研

需要的功能——协议兼容、虚拟 key、按 key 配额与用量统计、多后端路由、失败重试——LiteLLM 全都开箱即有。自研这套要一到两周，而且协议兼容的长尾坑（流式格式、`tool_calls` 结构、各家 SDK 的参数差异）会持续消耗时间。

**代价**：引入一个 Python 服务，高并发下网关本身可能成为瓶颈；部分功能（如 Prometheus 指标）在某些版本属于企业版。

**何时重新评估**：网关 CPU 打满，或网关引入的延迟超过 20ms P99。届时数据模型和 API 语义已经稳定，用 Go 重写的风险可控。

### 逻辑模型名与真实模型解耦

业务方调 `aqueduct-chat`，不是 `Qwen3-235B-A22B-FP8`。换模型、灰度、把某个业务单独切到新模型，都只改网关配置。

**代价**：多一层间接，排障时需要多查一次映射关系。

这是整个设计里最便宜也最重要的一个决定。真实模型名一旦进入业务代码，以后每次换模型都要协调所有调用方，实际上就换不动了。

### 模型选 MoE + FP8

H20 的特点是显存大（96GB/卡）、带宽高（4.0TB/s）、算力弱（约为 H100 的 1/6.7）。MoE 模型参数总量大但每次只激活一小部分，正好用得起大显存、享受得到高带宽、绕得开弱算力。同等能力下稠密模型在 H20 上的解码速度明显吃亏。

FP8 量化把权重占用减半，多出来的显存全部给 KV cache，直接换成并发数。

**代价**：FP8 有量化损失，KV cache 用 FP8 时损失更明显一些。上线前需要用内部真实任务做一次质量对比。

详细测算见 [../hardware.md](../hardware.md)。

## 4. 硬件约束

这一节的结论决定了后面所有的调优方向，值得单独强调。

H20 是算力被削、显存和带宽反而更强的卡。推理的两个阶段受影响完全相反：

- **预填充是算力密集的** → H20 明显慢，只有 H100 的 15% 左右。
- **解码是带宽密集的** → H20 比 H100 还快一点。

**所以 Aqueduct 的性能画像是：首 token 慢、生成快。** 一个 32k token 的长提示词，首字可能要等好几秒；但一旦开始吐字，速度不输任何卡。

由此推出三条贯穿整个部署的原则：

1. **优化重心放在减少重复预填充上，不是堆并发。** 前缀缓存是这套硬件上性价比最高的优化，必须开，而且要推动业务方把系统提示词写成稳定前缀。
2. **必须开分块预填充。** 否则一个长上下文请求会把所有正在生成的请求卡住数秒，尾延迟无法接受。
3. **调度参数不能照抄 H100 的配置。** 具体数值和理由见 [lld.md](lld.md) 的配置项一节。

硬件已确认为 **H20 96GB 版本，单机 8 卡共 768GB 显存**。据此定下的能力边界：主力模型用 235B 级 MoE 加 FP8，权重约 235GB，留约 470GB 给 KV cache。671B 级模型在这台机器上不可用——权重就吃掉 671GB，剩下的撑不起可用并发。

## 5. 非功能设计

### 性能目标

**这些是待验证的目标值，不是承诺。** 压测跑完后按实测修正，在此之前不要向业务方报任何数字。

| 指标 | 目标 | 说明 |
|---|---|---|
| TTFT P50（2k 输入） | < 1s | 短提示词的常规体验 |
| TTFT P99（32k 输入，缓存未命中） | 待实测 | H20 的短板，预期数秒级 |
| TPOT | < 50ms | 约 20 字/秒，流式阅读体验的下限 |
| 并发（32k 上下文） | 数十路 | 由 KV cache 容量决定 |
| 网关额外延迟 P99 | < 20ms | 超过就该考虑重写网关 |

### 可用性

起步阶段**是单点**：一台 GPU 机器、一个 vLLM 实例。机器故障或模型重启即服务不可用，恢复时间取决于权重加载，几分钟到几十分钟。

这是刻意的取舍。内部服务，先跑起来比先做高可用重要。但架构上预留了扩展路径，达成任一条都不需要改代码：

- **加 GPU 机器** → 网关配置里同一逻辑模型下加一行后端地址，自动负载均衡。
- **网关高可用** → 网关无状态，起多个实例挂在四层负载均衡后，PostgreSQL 单独部署。
- **上新模型** → 起一个新 vLLM 实例，网关加一个逻辑模型名。

对业务方的要求写在接入文档里：必须处理 5xx 和超时，关键路径要有降级方案。

### 安全

- **鉴权**：每个接入方一个虚拟 key，绑定可访问模型和周期预算。底层 vLLM 的 key 不下发给任何业务方。
- **网络**：全部服务只监听内网。vLLM 端口只对网关地址开放——vLLM 本身没有配额和限流，任何能直连它的人都能打满整台机器。
- **密钥管理**：所有密钥走环境变量，从 `.env` 读取，`.env` 不入库，仓库里只有 `.env.example`。
- **日志**：默认只记 token 数和元数据，**不记请求和响应正文**。排障需要时临时开启，并明确关闭时间。
- **数据不出境**：全部模型本地部署，请求不经过任何外部 API。

最后一条是这个项目最重要的合规价值。**不要为了补齐某个能力而在网关里挂外部模型**——那会让整个数据边界失效，而且业务方无从察觉自己的数据出去了。如果确实需要，必须用独立的逻辑模型名前缀（如 `external-`）明确标识，并单独审批。

### 可观测性

指标分三层看，对应三类问题：

- **业务层**（网关）：谁在调、调了多少、错误率多少 → 回答"这个服务有人用吗、用得对吗"。
- **引擎层**（vLLM）：TTFT、TPOT、排队长度、KV cache 使用率、前缀缓存命中率 → 回答"慢在哪一步"。
- **硬件层**（DCGM）：GPU 利用率、显存、温度、功耗 → 回答"是不是机器的问题"。

具体指标名和告警阈值见 [lld.md](lld.md)。

## 6. 部署架构

### 阶段一：单机

网关和推理跑在同一台 GPU 机器上，最省事。

```
┌──────────── GPU 机器 ────────────┐
│                                  │
│  LiteLLM :4000  ←── 内网调用方    │
│      │                           │
│      ▼                           │
│  vLLM :8000  (8×H20, TP=8)       │
│                                  │
│  PostgreSQL :5432 (容器内)        │
└──────────────────────────────────┘
```

端口暴露原则：4000 对内网开放，8000 和 5432 只监听回环。

### 阶段二：多机

**扩展方式唯一：加同规格的 8 卡 96GB H20 机器。** 不换更大显存的卡，不引入异构硬件。

第二台机器到位后，网关移到独立的普通机器，GPU 机器只跑推理。

```
┌── 网关机（普通机器）──┐
│  LiteLLM :4000       │ ←── 内网调用方
│  PostgreSQL :5432    │
└──────────┬───────────┘
           │  内网，仅网关地址可达 GPU 机器的 8000
     ┌─────┴─────┐
     ▼           ▼
┌─────────┐ ┌─────────┐
│ GPU 机 1 │ │ GPU 机 2 │   ← 同规格，可互换
│ 8×H20    │ │ 8×H20    │
│ 主力 TP=8│ │ 主力副本  │
└─────────┘ └─────────┘
```

同构带来三个具体简化，都体现在这套设计里：

- **容量线性可加**，一台的实测吞吐乘以台数即可，不必为不同规格分别测算。
- **配置复用**，每台的模型参数除地址外完全一致，加机器是复制而非重新设计。
- **任何模型可跑在任何一台上**，路由和故障转移不需要考虑规格差异。

因此设计里**不为异构硬件预留抽象层**——没跑过的扩展点只会增加复杂度。

**默认做多副本**：每台独立跑完整模型，网关负载均衡。扩容线性、故障隔离、对网络无特殊要求。第二台的第一优先用途是**消除单点**，不是加模型种类。

具体的卡位分配方案（含拆卡跑小模型的取舍）见 [../hardware.md](../hardware.md) 的扩展一节。

**跨机张量并行目前不做。** 它是跑 671B 级模型的唯一出路，但前提是 ≥200Gbps 的 RDMA 网络，当前既无需求也无该网络。真要上时是一次独立的架构决策，不是"加台机器"。

## 7. 演进路线

每个阶段有明确的退出标准，没达成就不进下一阶段。

**阶段 0：机器到货前（当前）**
交付部署配置、脚本、文档。退出标准：机器到货后能按手册一次跑通。

**阶段 1：单机单模型跑通**
部署主力模型，压测定容量，签发第一批 key 给 2–3 个种子业务。
退出标准：冒烟测试全过；压测数据填进手册；种子业务连续一周正常调用。

**阶段 2：可观测与稳定性**
接入 Grafana 面板和告警，补齐故障处理手册，做一次模型质量回归基线。
退出标准：能在告警响起后十分钟内定位到是哪一层的问题。

**阶段 3：扩容与消除单点**
第二台机器上线，跑主力模型的副本，验证多副本负载均衡与故障转移。
退出标准：**任意一台机器下线不影响服务**。

小模型（`aqueduct-fast`、`aqueduct-embed`）在这一阶段之后再考虑——它们要拆卡，会牺牲主力模型的容量均衡。先把高可用做扎实，再谈模型种类。

**阶段 4（可选）：开源**
脱敏、补英文文档和许可证、去掉环境特定假设。
前置条件：阶段 1–3 全部完成，且有实测数据可以公开。没跑过的东西开源出去只是负担。

## 8. 风险与待定

| 项 | 影响 | 处理 |
|---|---|---|
| 所有性能数字未经实测 | 容量规划可能整体偏离 | 阶段 1 压测后全面修正，在此之前不对外承诺 |
| 机器台数未定 | 决定何时能消除单点、何时能上小模型 | 扩展方式已定（加同规格机器），台数不影响架构，只影响排期 |
| FP8 量化的质量损失未评估 | 可能影响业务效果 | 阶段 1 用内部真实任务做 FP8 与 BF16 对比 |
| 单点，无高可用 | 机器故障即服务中断 | 已知并接受；对业务方明示，要求其处理失败 |
| LiteLLM 部分能力属企业版 | 指标或某些功能可能不可用 | 首次部署时验证，不可用则退回 vLLM 自身指标加数据库查询 |
| 模型版本迭代快 | 文档里的模型名可能已过时 | 下载前核对官方仓库，不照抄文档 |
